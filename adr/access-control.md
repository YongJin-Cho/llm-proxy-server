# 프록시 및 모니터링 UI 접근 통제

## Concern
프록시 엔드포인트와 모니터링 UI에 어떤 최소 인증·접근 통제를 적용해야 하는가?

## Status
approved

## Context
- 인증 없는 프록시는 제3자의 무단 모델 사용과 비용 발생 위험이 있다.
- 모니터링 UI는 저장된 요청·응답 본문을 보여줄 수 있으므로 보호가 필요하다.
- 초기 제품은 완성형 사용자·조직 권한 관리가 아니라 로컬 또는 단일 운영 환경을 대상으로 한다.

## Decision
**Option B — 인증 없이 로컬호스트 바인딩.** 초기 제품은 프록시와 모니터링 UI를 localhost에만 바인딩하고 별도 인증은 적용하지 않는다. 네트워크에 노출하는 배포는 현재 범위에서 지원하지 않는다.

## Options
### Option A — 공유 프록시 키와 관리 UI 키
- 프록시 API는 설정된 공유 API 키를 요구한다.
- 모니터링 UI와 로그 API는 별도의 관리 키를 요구한다.
- Pro: 구현이 단순하고 프록시와 관리면을 분리할 수 있다.
- Con: 사용자별 권한·감사 기능은 제공하지 않는다.

### Option B — 인증 없이 로컬호스트 바인딩
- 인증은 생략하고 서버를 localhost에만 바인딩한다.
- Pro: 로컬 개발이 가장 간단하다.
- Con: 네트워크 노출 시 보호가 없고, 설정 실수의 위험이 크다.

### Option C — 외부 OIDC/JWT 기반 인증
- 프록시와 UI를 외부 인증 제공자와 연동한다.
- Pro: 운영 환경의 사용자·권한 관리가 강력하다.
- Con: 초기 제품에 외부 의존성과 설정 복잡도가 크다.

## Tradeoffs
| | Option A | Option B | Option C |
|---|---|---|---|
| 초기 구현 | 낮음 | 매우 낮음 | 높음 |
| 네트워크 노출 보호 | 높음 | 낮음 | 높음 |
| 사용자별 권한 | 없음 | 없음 | 있음 |
| 외부 의존성 | 없음 | 없음 | 있음 |

## Recommendation
- 초기 단일 운영자 제품에는 Option A를 권장한다. 인증 설정이 없을 때는 안전한 실패로 요청을 거절하고, 운영자는 명시적으로 키를 설정해야 한다.

## Consequences
- 프록시 키와 관리 UI 키를 설정으로 주입해야 한다.
- 키 비교, 오류 응답, UI 세션 또는 요청 헤더 전달 방식을 Spec에 명시해야 한다.
- 사용자별 RBAC와 OIDC 연동은 초기 범위에서 제외한다.

## Downstream Concerns
- [x] **directly resolved — 외부 노출:** localhost 바인딩을 전제로 하며, 외부 네트워크 노출·리버스 프록시 인증 설정은 초기 범위에서 지원하지 않는다.
- [x] **out of scope — 사용자별 RBAC:** 초기 단일 운영자 범위를 벗어난다.

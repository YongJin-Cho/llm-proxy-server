# 스트리밍 응답 처리

## Concern
OpenAI Responses API의 스트리밍 응답을 프록시가 어떻게 전달하고 저장해야 하는가?

## Status
approved

## Context
- AC-001에서 초기 API 계약으로 `/v1/responses` 중심 범위를 선택했다.
- 클라이언트는 장시간 응답을 기다리지 않고 토큰·이벤트를 점진적으로 받아야 할 수 있다.
- 요청·응답 로그는 스트리밍 중에도 유실되지 않고 완료·오류 상태를 구분해야 한다.

## Decision
**Option A — SSE 스트리밍 전달 및 종료 후 집계 로그.** 제공자의 SSE 이벤트를 클라이언트에 전달하고, 스트림 종료 시 최종 상태와 집계된 요청·응답 로그를 저장한다.

## Options
### Option A — SSE 스트리밍 전달 및 종료 후 집계 로그
- 제공자의 SSE 이벤트를 프록시가 거의 그대로 클라이언트에 전달한다.
- 연결 종료 후 개별 `data` event를 provider API 계약에 맞는 최종 응답 하나로 통합해 하나의 집계 로그로 저장한다.
- Pro: OpenAI 호환성이 높고 구현·클라이언트 처리가 단순하다.
- Con: 연결 중 장애가 발생하면 완료 전 로그를 별도로 보완해야 한다.

### Option B — 프록시가 이벤트를 정규화해 전달하고 청크별 저장
- 제공자 이벤트를 내부 이벤트 모델로 변환하고 각 청크 또는 이벤트를 저장한다.
- Pro: 제공자별 확장과 실시간 모니터링에 유리하다.
- Con: 초기 구현·저장량·복구 로직이 복잡해진다.

### Option C — 비스트리밍만 지원
- 초기 범위에서는 `stream: false` 요청만 허용하고 스트리밍은 명확히 거절한다.
- Pro: 로그 완결성과 테스트가 가장 단순하다.
- Con: 대화형 클라이언트 호환성과 사용자 경험이 제한된다.

## Tradeoffs
| | Option A | Option B | Option C |
|---|---|---|---|
| 클라이언트 호환성 | 높음 | 높음 | 낮음 |
| 초기 복잡도 | 중간 | 높음 | 낮음 |
| 로그 세밀도 | 집계 중심 | 이벤트 중심 | 집계 중심 |
| 확장성 | 중간 | 높음 | 낮음 |

## Recommendation
- 초기 제품의 호환성과 구현 균형을 위해 Option A를 권장한다.

## Consequences
- SSE 헤더, 이벤트 종료 규칙, 연결 오류 처리, 최종 통합 응답 생성 규칙, 집계 로그 스키마를 Spec에 명시해야 한다.
- 이벤트별 영구 저장과 실시간 UI 갱신은 초기 범위에서 제외할 수 있다.

## Downstream Concerns
- [x] **deferred assumption — 스트리밍 로그 장애 복구:** 초기에는 연결 종료·전송 오류 시 부분 결과를 `failed` 상태의 집계 로그로 저장하며, 재처리는 후속 범위로 둔다.
- [x] **deferred assumption — 실시간 UI:** UI는 초기에는 완료·실패한 집계 로그를 조회하며, 스트리밍 중 실시간 갱신은 후속 범위로 둔다.
